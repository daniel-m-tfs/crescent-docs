O que é o Crescent

Crescent é um framework web em Lua que roda sobre o OpenResty (Nginx + LuaJIT) e usa MySQL. O Nginx cuida do HTTP (TLS, workers, keep-alive, limites, arquivos estáticos); o Crescent cuida de rotas, middleware, validação, ORM, migrations, templates, segurança e CLI.

Esta documentação é da versão 2.0. Vindo do Crescent 1.x (Luvit)? Veja Migrando do 1.x.

Requisitos

Com Docker Sem Docker
Docker com Compose OpenResty (inclui resty, lua-resty-mysql, lua-resty-openssl)
— LuaRocks (para instalar etlua, lua-resty-http, lua-resty-mail)
— MySQL 8 ou MariaDB

Criando um projeto

O jeito mais rápido é partir do template crescent-starter: ele já traz um hello world, Docker, MySQL e a CLI.

git clone https://github.com/daniel-m-tfs/crescent-starter.git meu-app
cd meu-app

Se você tem o repositório do framework, lua cli.lua new meu-app gera o mesmo projeto e já cria o .env com APP_KEY e JWT_SECRET aleatórios (pule o cp abaixo).

Com Docker (recomendado)

lua cli.lua setup    # git do zero, usuário/senha do MySQL e sobe o Docker

O setup pergunta antes de cada passo (Enter aceita o padrão): recomeça o histórico do git sem o remote do template e adiciona o seu remote (opcional), grava usuário e senha do banco no .env (que ele cria com APP_KEY e JWT_SECRET aleatórios) e sobe a aplicação com hot reload. Depois, no dia a dia:

lua cli.lua run      # sobe app + MySQL (hot reload)
lua cli.lua rerun    # reconstrói a imagem: Dockerfile, dependências ou Nginx mudaram
lua cli.lua stop     # para, mantendo o banco

Pronto:

  • http://127.0.0.1:8080 — página hello world
  • /api/hello?name=Ada — exemplo JSON com validação
  • /health e /ready — liveness e readiness (verifica o banco)

O código fica montado no container com recarga automática (edite e recarregue a página) e as migrations pendentes rodam ao subir. Rode a CLI dentro do container:

docker compose exec app bin/crescent routes

Sem Docker

./deps.sh                      # instala as dependências Lua em ./lua_modules
cp .env.example .env           # ajuste DB_* para o seu MySQL
lua cli.lua server start       # http://127.0.0.1:8080
curl http://127.0.0.1:8080/health

O deps.sh encontra o LuaJIT do OpenResty (Homebrew, /usr/local/openresty ou /opt/openresty); para outro local, use OPENRESTY_LUAJIT=/caminho/luajit ./deps.sh.

lua cli.lua server stop para o servidor. Em desenvolvimento o nginx.conf usa lua_code_cache off, então alterações no código valem na próxima requisição.

O app.lua gerado:

local Crescent = require("crescent")
local Config = require("crescent.config")

local app = Crescent.new(Config.load())

app:use(Crescent.middleware.security_headers.create())
app:use(Crescent.middleware.request_log.create({
    skip = function(ctx) return ctx.path == "/health" or ctx.path == "/ready" end,
}))

require("src.health").register(app)
require("src.hello").register(app)

return app

A aplicação

O app.lua cria a aplicação com Crescent.new(config), registra middlewares e módulos e retorna o app. O Nginx executa esse arquivo uma vez por worker e, a cada requisição, chama require("app"):run():

location / {
    content_by_lua_block {
        require("app"):run()
    }
}

Consequências práticas:

  • Código no topo de app.lua e dos módulos roda uma vez por worker, não por requisição. Não guarde estado de requisição em variáveis de módulo; use ctx.state.
  • Em produção (lua_code_cache on) é preciso recarregar o Nginx para aplicar mudanças. Em desenvolvimento o nginx.conf usa lua_code_cache off e recarrega o código a cada requisição.
  • O Nginx de produção constrói o app já no init_by_lua_block: um erro de configuração falha o start/reload em vez da primeira requisição.

Cada módulo expõe uma função register(app):

-- src/hello/init.lua
local controller = require("src.hello.controllers.hello")

local Module = {}

function Module.register(app)
    app:get("/", controller.index, "hello.index")
end

return Module

Configuração e ambiente

Config.load() carrega config/<APP_ENV>.lua (padrão development). Os arquivos de config leem variáveis com crescent.env:

-- config/production.lua
local Env = require("crescent.env")

return {
    environment = "production",
    debug = false,
    server = { host = "127.0.0.1", port = 8080, max_body_size = 5 * 1024 * 1024 },
    database = {
        host = Env.get("DB_HOST"),
        port = Env.number("DB_PORT", 3306),
        database = Env.get("DB_NAME"),
        user = Env.get("DB_USER"),
        password = Env.get("DB_PASSWORD"),
    },
}
Função Retorno
Env.get(nome, padrão) string; ordem: variável do processo, depois .env, depois o padrão
Env.number(nome, padrão) número (erro se o valor não for numérico)
Env.boolean(nome, padrão) true/false a partir de true, 1, yes, false, 0, no

Pegadinha do Nginx: o Nginx limpa o ambiente dos workers. Toda variável lida pela aplicação precisa de uma diretiva env NOME; no nginx.conf e nos arquivos de conf/, senão Env.get não a enxerga (em produção, sem .env, ela simplesmente vem vazia). Os arquivos gerados já declaram APP_*, DB_*, JWT_SECRET e SMTP_*.

O .env é só conveniência local; em produção use variáveis de ambiente de verdade. A porta é definida pelo listen do nginx.conf (o server.port da config é apenas validado).

Outras chaves aceitas pela config da aplicação:

Chave Uso
debug inclui detalhes internos nas respostas de erro e desativa o cache de templates
database conexão MySQL; quando tem database, o app configura o banco e expõe ctx.db
views_root / view_layout pasta dos templates (padrão views) e layout padrão
error_handler função (ctx, err) para erros não tratados (veja Erros)
logger instância de crescent.logger ou function(level, message, fields)
secret_key / secret_key_fallbacks segredo de cookies assinados, sessões e CSRF (padrão: APP_KEY)
upload_root / upload destino de ctx:save_upload e limites de upload

Rotas

app:get("/users", list_users)
app:post("/users", create_user)
app:put("/users/{id}", update_user)
app:patch("/users/{id}", patch_user)
app:delete("/users/{id}", delete_user)
Padrão Exemplo ctx.params
/users/{id} /users/42 { id = "42" }
/posts/{slug?} /posts e /posts/ola slug é nil quando ausente
/files/{path*} /files/a/b/c.txt { path = "a/b/c.txt" } (só no último segmento)

Parâmetros chegam sempre como string. Rotas estáticas têm prioridade sobre rotas com parâmetros, independentemente da ordem de registro.

Grupos e nomes:

app:group("/api/v1", function(api)
    api:get("/users/{id}", show_user, "users.show")   -- GET /api/v1/users/{id}
end)

app:route("users.show")   -- "/api/v1/users/{id}"
  • HEAD usa a rota GET automaticamente.
  • Caminho existente com outro método responde 405 com o header Allow; caminho inexistente responde 404 (route_not_found).
  • lua cli.lua routes lista todas as rotas com método, caminho e nome.

Controllers e o ctx

Um handler de rota é uma função que recebe o contexto da requisição (ctx) e responde. Nos módulos, os handlers ficam em controllers/ e delegam as regras de negócio para services/:

app:get("/users/{id}", function(ctx)
    local user = User:find_or_fail(ctx.params.id)
    return ctx:json(200, { data = user:to_table() })
end)

Dados da requisição

Campo Conteúdo
ctx.params parâmetros da rota
ctx.query query string (valores string; chave repetida vira lista)
ctx.body JSON ou form decodificado em tabela; outros tipos ficam como string
ctx.raw_body corpo original em texto
ctx.files arquivos de um multipart/form-data (veja Uploads)
ctx:get_header("User-Agent") header (nome sem diferenciar maiúsculas)
ctx:get_bearer() token de Authorization: Bearer ..., ou nil
ctx:cookie("nome") cookie (veja Cookies)
ctx.method, ctx.path, ctx.route método, caminho e padrão da rota encontrada
ctx.request_id, ctx.remote_addr id da requisição (também no header X-Request-Id) e IP do cliente
ctx.state tabela livre para passar dados entre middleware e action
ctx.db, ctx.config, ctx.app, ctx.debug banco, configuração, aplicação e modo debug

Um corpo JSON inválido é recusado antes da action com 400 malformed_json.

Respostas

Método Resposta
ctx:json(status, valor) JSON (application/json; charset=utf-8)
ctx:text(status, texto) texto puro
ctx:html(status, html) HTML
ctx:view(nome, dados, opções) template etlua (veja Views e layouts)
ctx:redirect(url, status) redirecionamento (padrão 302)
ctx:no_content() 204 sem corpo
ctx:error(status, mensagem, detalhes, código) erro JSON padronizado
ctx:header(nome, valor) define um header da resposta (encadeável)

Atalhos: retornar uma tabela envia 200 JSON e retornar uma string envia 200 texto. Uma action que não responde nem retorna nada gera 500 empty_response.

app:get("/ping", function() return { pong = true } end)   -- 200 {"pong":true}
  • ctx:redirect aceita só caminhos locais (/...); para outro domínio passe { allowed_hosts = { "exemplo.com" } } como terceiro argumento.
  • Para listas vazias em JSON use json.array({}) (de crescent.json), senão uma tabela vazia vira {}.
  • Models não viram JSON sozinhos: use model:to_table().

Middleware

Um middleware recebe (ctx, next). Chame next() para continuar; para bloquear, responda sem chamar next():

app:use(function(ctx, next)
    if ctx:get_header("X-Api-Key") ~= "segredo" then
        return ctx:error(401, "unauthorized", nil, "unauthorized")
    end
    ctx.state.client = "interno"
    return next()
end)
  • Middlewares rodam na ordem de app:use, antes do roteamento, em todas as requisições.
  • Código depois de next() roda depois da action. Para alterar headers da resposta nesse momento, use ctx.res:before_flush(function(res) ... end), pois a resposta normalmente já foi enviada quando next() retorna.
  • Para proteger uma rota só, envolva a action com auth.protect (aceita um middleware ou uma lista):
local auth = require("crescent.middleware.auth")

app:get("/admin", auth.protect({ auth.jwt(), require_admin }, admin_action))

lua cli.lua make:middleware nome gera o esqueleto em src/middleware/nome.lua. Os middlewares prontos (auth, CORS, rate limit, sessão, CSRF, headers de segurança, log) estão em Segurança e Utilitários.

Validação

app:validated(schema, action, origem) valida antes de chamar a action e responde 422 validation_failed com os erros por campo. A origem padrão é "body"; use "query" para a query string.

app:post("/users", app:validated({
    name = { required = true, string = true, min_length = 3, max_length = 50 },
    email = { required = true, email = true },
    age = { number = true, min = 18 },
    role = { custom = function(v) return v == "admin" or v == "user", "role inválido" end },
}, function(ctx)
    return ctx:json(201, ctx.body)
end))

Resposta de erro:

{
  "status": 422,
  "code": "validation_failed",
  "error": "validation failed",
  "details": { "name": [{ "code": "min_length", "message": "name must be at least 3 characters" }] }
}
Regra Valida
required presente e diferente de ""
type = "string" tipo Lua exato (interrompe as demais regras do campo)
string, number tipo do valor
min_length, max_length, length tamanho de strings (em caracteres UTF-8)
email, format e-mail simples; padrão Lua (format = "^%d+$")
min, max, range = { 1, 10 } limites de números
custom function(valor) que retorna true ou false, "mensagem"

Campos ausentes só falham com required. Valores de query string e de formulários são strings: number = true só passa para JSON; para query use format ou converta com tonumber na action.

Para validar manualmente: local ok, errors = ctx:validate(schema, "query").

Erros

Todo erro é um JSON com status, code (estável, para o cliente tratar) e error (mensagem); details é opcional:

return ctx:error(409, "e-mail já cadastrado", { field = "email" }, "email_taken")
-- 409 {"status":409,"code":"email_taken","error":"e-mail já cadastrado","details":{"field":"email"}}

Erros lançados (error(...)) dentro de controllers e middlewares:

  • Viram 500 internal_error e são registrados no log com o request id. O detalhe (mensagem e stack trace) só aparece na resposta com debug = true.
  • Uma tabela com status 4xx vira essa resposta, sem log de erro. É assim que Model:find_or_fail produz 404 model_not_found:
error({ status = 403, code = "no_access", public_message = "sem acesso" })
-- 403 {"status":403,"code":"no_access","error":"sem acesso"}

Para personalizar a resposta de erros 500, registre um handler (ele precisa responder):

app:on_error(function(ctx, err)
    return ctx:json(500, { error = "algo deu errado", request_id = ctx.request_id })
end)

Códigos que o próprio framework gera:

Código Status Quando
route_not_found 404 nenhuma rota para o caminho
method_not_allowed 405 caminho existe com outro método
validation_failed 422 app:validated
model_not_found 404 find_or_fail
malformed_json, malformed_form 400 corpo inválido
invalid_redirect 400 ctx:redirect para destino não permitido
internal_error, empty_response 500 erro não tratado; action sem resposta
template_error 500 falha ao renderizar um template

Autenticação, CSRF, CORS, rate limit e uploads têm seus próprios códigos (missing_credentials, csrf_invalid, rate_limited...), listados em Segurança.

Views e layouts

Templates usam etlua e ficam em views/. O nome inclui a extensão .etlua:

app:get("/", function(ctx)
    return ctx:view("hello/index.etlua", { title = "Início" }, { layout = "layout.etlua" })
end)
<!-- views/hello/index.etlua -->
<h1><%= title %></h1>
<ul>
  <% for _, item in ipairs(items or {}) do %>
    <li><%= item %></li>
  <% end %>
</ul>
<!-- views/layout.etlua -->
<!doctype html>
<html lang="pt-BR">
<head><title><%= title or "Crescent" %></title></head>
<body><%- content %></body>
</html>
  • <%= valor %> escapa HTML; <%- valor %> imprime sem escapar (use só com HTML confiável, como content e csrf_field()).
  • O layout recebe a página pronta em content e os mesmos dados da página.
  • Opções: status (padrão 200) e layout. Defina view_layout = "layout.etlua" na config para ter um layout padrão; layout = false desliga em uma página.
  • Helpers globais: app.view_renderer:helper("upper", function(s) return s:upper() end).
  • Com o middleware de sessão ativo, todo template recebe csrf_token() e csrf_field().
  • Templates ficam em cache quando debug = false.

Configuração

O Crescent 2.0 suporta somente MySQL/MariaDB, via lua-resty-mysql (não bloqueia o worker). A conexão vem de config.database:

-- config/development.lua
database = {
    host = Env.get("DB_HOST", "127.0.0.1"),
    port = Env.number("DB_PORT", 3306),
    database = Env.get("DB_NAME", "meu_app_dev"),
    user = Env.get("DB_USER", "crescent"),
    password = Env.get("DB_PASSWORD", ""),
},

Crescent.new(config) configura o banco no boot (sem abrir conexão: cada query pega uma conexão do pool do worker). A partir daí, models e query builder usam esse banco automaticamente, e os controllers o recebem em ctx.db.

Chave opcional Padrão Descrição
charset "utf8mb4" charset da conexão
connect_timeout / timeout 5000 / 10000 em ms
pool_size 100 conexões mantidas por worker
max_idle_timeout 10000 tempo ocioso no pool (ms)
ssl, ssl_verify — TLS com o MySQL

SQL direto, sempre com ? (os valores são escapados):

local rows, err = ctx.db:query("SELECT id, name FROM users WHERE email = ?", { email })
local result = ctx.db:execute("UPDATE users SET name = ? WHERE id = ?", { "Ada", 1 })
-- result = { affected_rows = 1, insert_id = 0 }

Erros retornam nil, err, errno, sqlstate, kind, em que kind é "unique_violation", "foreign_key_violation", "deadlock", "lock_timeout", "connection", "bind" ou "query".

Models

-- src/users/models/user.lua
local Model = require("crescent.model")

return Model:extend({
    table = "users",
    fillable = { "name", "email", "password" },  -- campos aceitos em create/update
    hidden = { "password" },                     -- fora de to_table()
    timestamps = true,                           -- created_at / updated_at
    validates = {
        name = { required = true, min_length = 3 },
        email = { required = true, email = true, unique = true },
    },
})

lua cli.lua make:model User users gera um esqueleto em src/users/models/user.lua. As regras de validates são as mesmas de Validação, mais unique = true (consulta o banco; mantenha também um índice UNIQUE).

CRUD

local User = require("src.users.models.user")

local user, errors = User:create({ name = "Ada", email = "ada@example.com" })
if not user then
    return ctx:error(422, "validation failed", errors, "validation_failed")
end

local user = User:find(1)                    -- model ou nil
local user = User:find_or_fail(1)            -- lança 404 model_not_found
local admins = User:where("role", "admin"):order_by("name"):get()
local first = User:where("email", email):first()
local total = User:count()

user.name = "Ada Lovelace"
user:save()                                  -- UPDATE só das colunas alteradas
user:update({ name = "Ada Byron" })          -- fill + save
user:delete()

return ctx:json(200, { data = user:to_table() })
  • create, save e update retornam o model, ou nil, erros. Erros de validação (e de chave única do MySQL) chegam como tabela { campo = { { code, message } } }; falhas de banco chegam como string.
  • User:where(...) aceita o mesmo encadeamento do query builder e termina em get(), first(), count() ou page().
  • user.name lê o atributo. Se a coluna tiver o nome de um método do model (table, save, update...), use user:get("coluna") e user:set("coluna", valor).
  • Converta para JSON com user:to_table(); ela respeita hidden e inclui relações carregadas.
  • O último argumento opcional de todos os métodos é o adaptador de banco (por exemplo, a transação tx).

Paginação

local result = User:where("active", 1):order_by("name"):page(ctx.query.page, ctx.query.per_page)
-- result.data = { models }
-- result.meta = { page, per_page, total, last_page, from, to }

Valores inválidos voltam ao padrão (página 1, 15 por página) e per_page é limitado a 100 (passe { max_per_page = n } como terceiro argumento para mudar).

Tipos das colunas (casts)

O MySQL devolve BIGINT como string. O model converte automaticamente a chave primária e colunas *_id para número. Para outras colunas, declare casts:

casts = { active = "boolean", price = "number", external_id = "string" },

Tipos: string, number, integer, boolean (1/0 vira true/false).

Soft deletes

return Model:extend({ table = "users", soft_deletes = true })   -- precisa da coluna deleted_at
  • user:delete() grava deleted_at; consultas passam a ignorar o registro.
  • User:with_trashed() inclui os apagados; User:only_trashed() traz só eles.
  • user:restore() desfaz; user:force_delete() apaga de verdade.

Hooks

Funções na definição do model que recebem a instância. Um hook before_* que retorna false cancela a operação.

before_save = function(user)
    user.email = user.email:lower()
end,

Disponíveis: before_save, before_create, before_update, after_create, after_update, after_save, before_delete, after_delete.

Relações

Declare as relações na tabela relations. model pode ser o nome do módulo (resolvido sob demanda, evita require circular):

-- users
relations = {
    posts = { type = "has_many", model = "src.blog.models.post" },
    profile = { type = "has_one", model = "src.users.models.profile" },
},

-- posts
relations = {
    user = { type = "belongs_to", model = "src.users.models.user" },
},
Tipo Chave estrangeira padrão
has_many, has_one singular da tabela do pai + _id, na tabela relacionada (users → user_id)
belongs_to singular da tabela relacionada + _id, na própria tabela

Informe foreign_key (e local_key/owner_key) quando o padrão não servir.

Eager loading com with: uma query por relação para todos os registros, sem N+1.

local users = User:with("posts"):get()
users[1].posts                    -- lista de Post

local posts = Post:with("user", "comments.author"):get()   -- relações aninhadas

-- restringir a query da relação
User:query():with({ posts = function(q) q:order_by("created_at", "DESC") end }):get()

Sem eager loading, user:get("posts") carrega a relação na primeira chamada (user.posts só funciona depois de carregada).

Query builder

Para consultas sem model (os resultados são tabelas simples):

local QueryBuilder = require("crescent.database.query_builder")

local rows = QueryBuilder.table("users")
    :select("users.id", "users.name", "profiles.bio")
    :left_join("profiles", "profiles.user_id", "users.id")
    :where("active", true)
    :where("age", ">=", 18)
    :where(function(q) q:where("role", "admin"):or_where("verified", true) end)
    :where_in("country", { "BR", "PT" })
    :order_by("users.name")
    :limit(20)
    :get()
Grupo Métodos
Filtros where, or_where, where_in, where_not_in, where_null, where_not_null, where_raw(sql, bindings)
Junções join, left_join, right_join
Ordem e limite order_by(coluna, "ASC" ou "DESC"), limit, offset, paginate(página, por_página)
Execução get(), first(), count(), exists(), page(página, por_página)
Escrita insert(valores), update(valores), delete()
Depuração to_sql() retorna sql, bindings sem executar
  • Operadores aceitos: =, !=, <>, <, <=, >, >=, LIKE, NOT LIKE. where("coluna", nil) gera IS NULL.
  • update e delete sem where lançam erro (proteção contra alterar a tabela inteira).
  • Linhas do query builder não passam pelos casts: ids BIGINT chegam como string.
  • QueryBuilder.raw(sql, bindings) executa SQL livre.

Transações

local Database = require("crescent.database")

local user, err = Database.transaction(function(tx)
    local user = assert(User:create({ name = "Ada", email = "ada@example.com" }, tx))
    tx:execute("INSERT INTO audit (user_id) VALUES (?)", { user.id })
    return user
end)
  • Faz COMMIT quando a função retorna normalmente e ROLLBACK quando ela lança erro, retorna false ou nil, err.
  • Passe tx como último argumento para models e query builder (User:create(attrs, tx), QueryBuilder.table("users"):get(tx)), senão eles usam outra conexão, fora da transação.
  • tx:transaction(fn) aninhado usa SAVEPOINT.

Migrations

lua cli.lua make:migration create_orders_table     # CREATE TABLE orders
lua cli.lua make:migration add_total_to_orders     # ALTER TABLE orders
lua cli.lua db:migrate                             # aplica as pendentes
lua cli.lua db:status                              # lista o que rodou
lua cli.lua db:rollback                            # desfaz o último lote (batch)

Cada migration retorna up e down, que devolvem uma string SQL ou uma lista delas:

return {
    up = function(db)
        return {
            [[CREATE TABLE `orders` (
                `id` BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
                `user_id` BIGINT UNSIGNED NOT NULL,
                `total` DECIMAL(10,2) NOT NULL,
                `created_at` TIMESTAMP NULL,
                `updated_at` TIMESTAMP NULL
            ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4]],
            "CREATE INDEX `orders_user_id` ON `orders` (`user_id`)",
        }
    end,
    down = function(db)
        return "DROP TABLE `orders`"
    end,
}
  • Os arquivos rodam em ordem de nome e ficam registrados na tabela migrations. Cada execução de db:migrate forma um lote.
  • O arquivo gerado por make:migration vem com uma tabela example de exemplo: edite antes de rodar.
  • DDL do MySQL faz commit implícito: migrations não rodam em transação. Se uma migration com vários comandos falhar no meio, ela fica parcialmente aplicada e sem registro. Prefira um comando de schema por migration.

Autenticação

crescent.middleware.auth traz middlewares para JWT, Bearer, Basic e API key. Em caso de sucesso eles colocam o usuário em ctx.state.user; em caso de falha respondem 401 sem chamar a action.

local auth = require("crescent.middleware.auth")

-- uma rota
app:get("/me", auth.protect(auth.jwt(), function(ctx)
    return ctx:json(200, ctx.state.user)
end))

-- todas as rotas registradas depois
app:use(auth.jwt())

auth.jwt() lê o segredo de JWT_SECRET (mínimo de 32 bytes; gere com openssl rand -base64 48). Sem ele, o app falha ao iniciar.

Middleware Uso
auth.jwt(opções) JWT de acesso no header Authorization: Bearer; define também ctx.state.jwt (payload)
auth.bearer(fn) token opaco; fn(token, ctx) retorna true, usuário ou false, "mensagem"
auth.basic(fn, { realm = "Admin" }) HTTP Basic; fn(usuário, senha, ctx)
auth.api_key("X-Api-Key", fn) chave em um header; fn(chave, ctx)
auth.protect(middleware, action) aplica um middleware (ou uma lista) a uma action

Opções de auth.jwt: secret, issuer, audience, algorithms (padrão { "HS256" }), leeway, optional = true (não bloqueia; só preenche o usuário se o token for válido) e get_user:

app:use(auth.jwt({
    get_user = function(payload, ctx)
        return User:find(payload.user_id)   -- nil → 401
    end,
}))

API key e Basic:

app:get("/internal", auth.protect(auth.api_key("X-Api-Key", function(key, ctx)
    if auth.secure_compare(key, os.getenv("INTERNAL_KEY") or "") then
        return true, { name = "servico-interno" }
    end
    return false, "invalid api key"
end), internal_action))

Use auth.secure_compare(a, b) para comparar segredos (tempo constante).

Login com JWT

local auth = require("crescent.middleware.auth")
local password = require("crescent.security.password")
local User = require("src.users.models.user")

app:post("/auth/login", app:validated({
    email = { required = true, email = true },
    password = { required = true },
}, function(ctx)
    local user = User:where("email", ctx.body.email):first()
    if not user or not password.verify(ctx.body.password, user.password) then
        return ctx:error(401, "invalid credentials", nil, "invalid_credentials")
    end
    return auth.generate_token_pair(user)
    -- { access_token, refresh_token, token_type = "Bearer", expires_in, refresh_expires_in }
end))

app:post("/auth/refresh", function(ctx)
    local ok, payload = auth.verify_refresh_token(ctx.body.refresh_token)
    if not ok then return ctx:error(401, "invalid token", nil, "invalid_token") end
    auth.revoke_token(payload)   -- o refresh token antigo deixa de valer
    return auth.generate_token_pair(payload.user_id)
end)

app:post("/auth/logout", auth.protect(auth.jwt(), function(ctx)
    auth.revoke_token(ctx.state.jwt)
    return ctx:no_content()
end))
  • O access token dura 15 minutos e o refresh token 30 dias (access_expires_in e refresh_expires_in, em segundos, mudam isso). O payload leva user_id, name e email.
  • auth.jwt() recusa refresh tokens; verify_refresh_token aceita só refresh tokens.
  • Tokens revogados ficam no lua_shared_dict crescent_jwt (compartilhado entre workers, já declarado no nginx.conf) até expirarem. O dict é perdido ao reiniciar o Nginx e não é compartilhado entre servidores.

Para assinar e verificar diretamente, use crescent.security.jwt:

local jwt = require("crescent.security.jwt")

local token = jwt.sign({ user_id = 1 }, secret, { expires_in = 900, issuer = "api" })
local ok, payload_or_message, code = jwt.verify(token, secret, { issuer = "api" })

Algoritmos HS256/HS384/HS512; o algoritmo é fixado por quem verifica (algorithms), nunca pelo token, e none nunca é aceito.

Senhas

local password = require("crescent.security.password")

local hash = password.hash("s3cr3t")          -- "600000$<salt>$<hash>"
password.verify("s3cr3t", hash)               -- true
password.needs_rehash(hash)                   -- true se as iterações mudaram

PBKDF2-HMAC-SHA256 com 600.000 iterações (recomendação OWASP), executado pelo OpenSSL. Cada hash leva dezenas de milissegundos e ocupa o worker: aplique rate limit no login. PASSWORD_HASH_ITERATIONS ajusta o padrão. Hashes gerados pelo Crescent 1.x continuam válidos.

CORS

Registre o CORS antes da autenticação, com app:use, para que o preflight (OPTIONS) seja respondido antes de exigir credenciais:

local cors = require("crescent.middleware.cors")

app:use(cors.create({
    origins = { "https://app.example.com" },   -- ou "*", ou function(origin, ctx)
    methods = { "GET", "POST", "PUT", "DELETE" },
    allowed_headers = { "Content-Type", "Authorization" },
    credentials = true,
    max_age = 600,
}))
  • O preflight é respondido com 204 pelo próprio middleware; não crie rotas OPTIONS.
  • cors.strict({ "https://app.example.com" }) liga credenciais, cache de preflight de 24 h e responde 403 a outras origens.
  • credentials = true com origins = "*" é recusado.

Headers de segurança

app:use(Crescent.middleware.security_headers.create({
    hsts = true,                                         -- só se o site for 100% HTTPS
    csp = "default-src 'self'; frame-ancestors 'none'",
}))

Sem opções, envia X-Content-Type-Options: nosniff, X-Frame-Options: DENY e Referrer-Policy: strict-origin-when-cross-origin (o app.lua gerado já registra esse middleware). Outras opções: frame_options, referrer_policy, permissions_policy, cross_origin_opener_policy e headers (extras; false remove um header).

Rate limit

local rate_limit = require("crescent.middleware.rate_limit")

app:use(rate_limit.create({ limit = 100, window = 60 }))   -- 100 req/min por IP

app:post("/auth/login", auth.protect(
    rate_limit.create({ limit = 5, window = 60, prefix = "rl:login:" }), login))
  • Janela fixa no lua_shared_dict crescent_limits, compartilhada entre workers.
  • Acima do limite: 429 rate_limited com Retry-After. Toda resposta traz X-RateLimit-Limit, X-RateLimit-Remaining e X-RateLimit-Reset.
  • Use um prefix diferente para cada limitador.
  • A chave padrão é o IP (ctx.remote_addr). Atrás de proxy, configure o realip do Nginx (veja Deploy); nunca use o X-Forwarded-For cru como chave. key = function(ctx) ... end personaliza; retornar nil isenta a requisição.

Sessões

local session = require("crescent.middleware.session")

app:use(session.create())   -- cookie criptografado (AES-256-GCM), 24 h, expira após 1 h sem uso
app:post("/login", function(ctx)
    local user = authenticate(ctx.body.email, ctx.body.password)
    if not user then
        ctx.session:flash("error", "credenciais inválidas")
        return ctx:redirect("/login")
    end
    ctx.session:regenerate()              -- sempre após login (evita session fixation)
    ctx.session:set("user_id", user.id)
    return ctx:redirect("/")
end)

app:post("/logout", function(ctx)
    ctx.session:destroy()
    return ctx:redirect("/")
end)
Método Efeito
get(k), set(k, v), delete(k) valores (serializáveis em JSON)
flash(k, v) / get_flash(k) valor disponível só na próxima requisição
regenerate() nova sessão com os mesmos dados
destroy() apaga a sessão e expira o cookie
clear(), is_new() limpa os valores; sessão criada nesta requisição
Opção Padrão
store "cookie" "shared" guarda os dados no lua_shared_dict crescent_sessions e o cookie leva só um id
name "crescent_session" nome do cookie
max_age / idle_timeout 86400 / 3600 segundos; false desativa
cookie { path = "/", same_site = "Lax", http_only = true } opções do cookie

O store cookie não guarda estado no servidor, mas tem limite de 4 KB (guarde ids, não objetos) e um cookie copiado continua válido até expirar. O store shared invalida a sessão de verdade no destroy, porém é perdido ao reiniciar o Nginx e não é compartilhado entre servidores.

CSRF

Formulários com login por cookie precisam de proteção CSRF. Registre o middleware depois da sessão:

local session = require("crescent.middleware.session")
local csrf = require("crescent.middleware.csrf")

app:use(session.create())
app:use(csrf.create({
    skip = function(ctx) return ctx:get_bearer() ~= nil end,   -- APIs com bearer token
}))

Nos templates, inclua o campo com <%- (sem escape, pois é HTML):

<form method="post" action="/posts">
  <%- csrf_field() %>
  <input name="title">
  <button>Salvar</button>
</form>

<meta name="csrf-token" content="<%= csrf_token() %>">

Requisições POST, PUT, PATCH e DELETE precisam enviar o token no campo _csrf ou no header X-CSRF-Token (para AJAX, leia a meta tag). Sem token válido: 403 csrf_invalid.

Uploads

Requisições multipart/form-data são lidas em streaming: os campos de texto vão para ctx.body e os arquivos para ctx.files, gravados em arquivos temporários.

app:post("/avatar", function(ctx)
    local file = ctx.files.avatar   -- { filename, content_type, size, path, field }
    if not file then return ctx:error(422, "avatar obrigatório", nil, "avatar_required") end
    if file.content_type ~= "image/png" then
        return ctx:error(422, "apenas PNG", nil, "invalid_type")
    end
    local path, err = ctx:save_upload(file, "avatars/" .. ctx.state.user.id .. ".png", { overwrite = true })
    if not path then return ctx:error(500, "falha ao salvar", nil, "upload_failed") end
    return ctx:json(201, { path = path })
end)

Configure o destino e os limites na config da aplicação:

upload_root = "storage",              -- única pasta em que save_upload grava (relativa ao projeto)
upload = {
    max_file_size = 10 * 1024 * 1024,
    max_files = 10,
    max_total_size = 50 * 1024 * 1024,
},
  • Temporários não salvos com ctx:save_upload são apagados ao fim da requisição.
  • filename e content_type vêm do cliente: valide o conteúdo e gere você o nome final. Caminhos com .. ou fora de upload_root são recusados.
  • Ajuste também client_max_body_size no nginx.conf.

arquivos ou campos demais 413 too_many_files, too_many_fields

    local res, err = api:get("/repos", { params = { page = 2 } })
    if not res then
        return ctx:error(502, "upstream failed", ctx.debug and err.message or nil, "upstream_error")
    end
    return ctx:json(200, res.data)
end)
  • Métodos: get(url, config), delete, head, options, e post(url, dados, config), put, patch.
  • Uma tabela em dados é enviada como JSON; uma string vai como está.
  • A resposta é { status, headers, body, data }; data é o JSON já decodificado (ou o corpo bruto).
  • Falhas de rede e status >= 400 retornam nil, err, com err.message e, quando houve resposta, err.status e err.data.
  • TLS é verificado por padrão, redirecionamentos não são seguidos e respostas acima de 10 MiB são abortadas (max_response_size).
  • Para chamadas avulsas: HttpClient.get(url).

O Nginx resolve DNS e verifica certificados para o Lua: os nginx.conf gerados já trazem resolver e lua_ssl_trusted_certificate. Sem eles, nomes não resolvem e conexões HTTPS falham. O cliente funciona em controllers, middlewares e timers, mas não em init_by_lua.

E-mail

crescent.mail envia por SMTP (com STARTTLS) sobre lua-resty-mail. Os dados do servidor vêm das variáveis SMTP_SERVER, SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_FROM e SMTP_FROM_NAME, ou podem ser passados em Mail.new({ server, port, user, password, from, from_name }):

local Mail = require("crescent.mail")

local mailer = Mail.new()

local ok, err = mailer:send({
    to = { "ada@example.com", { email = "grace@example.com", name = "Grace" } },
    subject = "Bem-vinda",
    text = "Olá!",
    html = "<p>Olá!</p>",
})
if not ok then ctx.state.log:error("falha no e-mail", { error = err }) end
  • Também aceita cc, bcc e reply_to.
  • Atalhos: send_text(para, assunto, texto), send_html(para, assunto, html) e send_template(para, assunto, "emails/welcome.etlua", dados), que renderiza um template de views/.
  • Porta 465 usa TLS direto; as demais usam STARTTLS.
  • Envie fora do caminho crítico quando possível: o envio espera a resposta do servidor SMTP.

Logs

crescent.logger grava uma linha JSON por entrada no error log do Nginx (no Docker, em stderr). Campos sensíveis são mascarados automaticamente:

local Logger = require("crescent.logger")

local log = Logger.new({ level = "info", fields = { service = "api" } })
log:info("login", { user_id = 7, password = "x" })
-- {"level":"info","msg":"login","service":"api","user_id":7,"password":"[REDACTED]"}

log:with({ request_id = ctx.request_id }):warn("cota excedida")
  • Níveis: debug, info, warn, error; entradas abaixo de level são ignoradas.
  • Mascarados (por substring no nome do campo): password, passwd, secret, token, authorization, cookie, api_key, credit_card, card_number, cvv, private_key. Acrescente outros com Logger.new({ redact = { "cpf" } }).
  • Logger.redact(tabela, { "cpf" }) devolve uma cópia mascarada.

Log por requisição

O app.lua gerado registra request_log, que grava uma entrada por requisição com método, caminho, rota, status, duração, IP, user_id (de ctx.state.user) e request id. Status 5xx saem como error e 4xx como warn.

app:use(Crescent.middleware.request_log.create({
    skip = function(ctx) return ctx.path == "/health" or ctx.path == "/ready" end,
}))

-- nos controllers, um logger já com o request id:
ctx.state.log:info("pedido criado", { order_id = order.id })

Todo erro 500 também é registrado pela aplicação com request id, método e caminho. Para usar seu próprio logger nesses registros: Crescent.new({ logger = Logger.new({ level = "warn" }) }).

JSON

crescent.json envolve o cjson com a política do framework:

local json = require("crescent.json")

json.encode({ ok = true })            -- '{"ok":true}'
json.decode('{"items":[]}')           -- items continua lista ao reenviar
json.array({})                        -- força [] em vez de {}

Tabelas vazias viram {} em JSON. Para listas que podem estar vazias na resposta, use json.array(lista). Barras não são escapadas ("/a" em vez de "\/a").

Health e readiness

crescent.health registra dois endpoints (o projeto gerado já faz isso em src/health):

require("crescent.health").register(app, {
    service = "api",
    checks = {
        database = require("crescent.health").checks.database,
        cache = function(ctx) return redis_ping() end,   -- true, ou nil e erro
    },
})
Endpoint Resposta
GET /health 200 enquanto o worker responde; não consulta dependências
GET /ready 200 se todos os checks passam, 503 caso contrário, com status e duração de cada check

Sem checks, /ready verifica o banco (SELECT 1) quando há um configurado. Mensagens de erro dos checks só aparecem na resposta com debug = true; sempre vão para o log. Use /health para reiniciar o processo e /ready para o balanceador decidir se envia tráfego.

Imagem Docker

O Dockerfile do projeto gera a imagem de produção:

docker build -t meu-app .

docker run -d -p 8080:8080 \
  -e APP_ENV=production \
  -e DB_HOST=db.interno -e DB_NAME=meu_app -e DB_USER=meu_app -e DB_PASSWORD=... \
  -e APP_KEY=... -e JWT_SECRET=... \
  -e RUN_MIGRATIONS=true \
  meu-app

O que a imagem faz:

  • Parte de openresty/openresty:*-alpine-fat e instala as dependências Lua em uma camada própria.
  • Roda como o usuário sem privilégios crescent; só logs/, tmp/ e storage/ são graváveis. Uploads vão para storage/ (upload_root = "storage"): monte um volume nesse caminho para que sobrevivam a novos containers (o docker-compose.yml de desenvolvimento já usa o volume app-storage).
  • Usa conf/nginx.docker.conf: cache de código ligado, worker_processes auto, app construído no init_by_lua e logs em stdout/stderr.
  • Tem HEALTHCHECK em /health.
  • Com RUN_MIGRATIONS=true, o entrypoint roda bin/crescent db:migrate antes de subir (até 10 tentativas, a cada 3 s, enquanto o banco não responde). O padrão da imagem é false.

Para rodar um comando avulso com a mesma imagem, passe-o como argumento:

docker run --rm --env-file prod.env meu-app bin/crescent db:migrate

Com várias réplicas, prefira rodar as migrations uma vez, num passo do deploy, em vez de RUN_MIGRATIONS=true em todas.

Docker Compose (desenvolvimento)

O docker-compose.yml é para desenvolvimento:

cp .env.example .env
docker compose up --build
  • Sobe a app e um MySQL 8.4 (exposto só em 127.0.0.1:3307; dados no volume mysql-data).
  • Usa conf/nginx.docker-dev.conf: um worker e lua_code_cache off, com o código montado em /app para recarga automática.
  • Roda as migrations pendentes ao subir e cria o banco de testes (DB_TEST_NAME) na primeira inicialização do volume.
  • APP_PORT muda a porta no host. As senhas do .env.example são só para desenvolvimento.

Não use esse arquivo em produção: ele monta o código-fonte e desliga o cache de código.

Sem Docker

Instale OpenResty, LuaRocks e as dependências (./deps.sh) no servidor e use conf/nginx.production.conf (revise antes):

APP_ENV=production openresty -p /srv/app/ -c conf/nginx.production.conf

# ou, de dentro do projeto
bin/crescent server start --conf conf/nginx.production.conf --env production
  • -p é a raiz do projeto (com / no final): caminhos relativos, .env, logs/ e o lua_package_path partem dela.
  • O arquivo traz user nobody; (só tem efeito quando o master roda como root), worker_processes auto, lua_code_cache on, access log em JSON e timeouts de cliente.
  • O init_by_lua_block { require("app") } constrói o app no master: um erro de configuração faz o start ou o reload falhar, em vez de quebrar a primeira requisição.
  • Deploy de código novo: atualize os arquivos e rode openresty -p /srv/app/ -c conf/nginx.production.conf -s reload (ou bin/crescent server reload --conf conf/nginx.production.conf).
  • O caminho do bundle de CAs (lua_ssl_trusted_certificate) é o do Debian/Ubuntu; ajuste em outras distribuições.

Use o supervisor do seu sistema (systemd, por exemplo) para iniciar o OpenResty no boot e repassar as variáveis de ambiente.

Variáveis de ambiente

Variável Uso
APP_ENV ambiente (development, production, test); escolhe config/<APP_ENV>.lua
APP_DEBUG true mostra detalhes de erros (só desenvolvimento)
APP_KEY segredo de cookies assinados, sessões e CSRF (32+ caracteres)
DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD conexão MySQL
DB_TEST_NAME banco usado pelo ambiente test
JWT_SECRET segredo do auth.jwt() (32+ bytes)
PASSWORD_HASH_ITERATIONS iterações do PBKDF2 (padrão 600000)
SMTP_SERVER, SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_FROM, SMTP_FROM_NAME e-mail
NGINX_CONF, RUN_MIGRATIONS Docker: configuração do Nginx e migrations ao subir
APP_PORT, DB_FORWARD_PORT, DB_ROOT_PASSWORD Docker Compose

Gere segredos com openssl rand -base64 48.

Cada variável lida pela aplicação precisa de uma diretiva env NOME; em todos os arquivos do Nginx que você usa (nginx.conf e conf/*.conf). Ao criar uma variável nova, acrescente a diretiva, senão ela chega vazia nos workers.

TLS, proxy e IP real

Normalmente o TLS termina num balanceador ou proxy na frente do OpenResty. Nesse caso, faça o Nginx confiar no IP informado pelo proxy, descomentando no conf/nginx.production.conf (ou nginx.docker.conf):

set_real_ip_from 10.0.0.0/8;          # rede do seu balanceador
real_ip_header X-Forwarded-For;
real_ip_recursive on;

Assim ctx.remote_addr (usado pelo rate limit e pelos logs) passa a ser o IP do cliente. Nunca confie no X-Forwarded-For sem isso: qualquer cliente pode forjá-lo.

Para terminar o TLS no próprio OpenResty, ajuste o bloco server:

server {
    listen 443 ssl;
    server_name app.example.com;
    ssl_certificate     /etc/letsencrypt/live/app.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.example.com/privkey.pem;

    location /public/ {
        alias public/;
        expires 1h;
    }

    location / {
        content_by_lua_block {
            require("app"):run()
        }
    }
}

Com o site 100% em HTTPS, ligue hsts = true no middleware de headers de segurança. Arquivos estáticos ficam em public/ e são servidos pelo Nginx em /public/, sem passar pelo Lua.

Logs e observabilidade

  • Access log do Nginx: uma linha JSON por requisição com horário, request id (rid), IP, método, URI, status, bytes e duração. É a fonte de verdade do tráfego.
  • Error log: erros do Nginx e as entradas JSON do crescent.logger (log por requisição, erros 500 com request id).
  • No Docker, os dois vão para stdout/stderr (docker logs); fora dele, para logs/.
  • X-Request-Id: o Crescent mantém o do proxy quando ele envia um, senão usa o $request_id do Nginx, e devolve o valor na resposta. Use-o para cruzar logs.
  • /health (liveness) e /ready (readiness, verifica o banco). Veja Health e readiness.

Checklist de produção

  • APP_ENV=production e debug = false (o config/production.lua já define).
  • APP_KEY e JWT_SECRET com 32+ caracteres, fora do repositório; nada de .env em produção.
  • Usuário do MySQL com acesso só ao banco da aplicação; migrations aplicadas no deploy.
  • Toda variável nova declarada com env NOME; nos arquivos do Nginx.
  • client_max_body_size e limites de upload ajustados ao que a aplicação aceita.
  • set_real_ip_from configurado se houver proxy; rate limit no login.
  • HSTS só com HTTPS em todo o site; CORS com lista explícita de origens.
  • Balanceador usando /ready; orquestrador reiniciando por /health.
  • lua_shared_dict (crescent_limits, crescent_jwt, crescent_sessions) mantidos no conf; lembre que eles são locais a cada servidor.

O que mudou

O Crescent 2.0 é uma reescrita: troca o Luvit pelo OpenResty (Nginx + LuaJIT). O Nginx passa a cuidar do servidor HTTP, dos workers e dos arquivos estáticos, e o banco continua sendo MySQL. A organização em módulos (src/<módulo> com controllers, services, models e rotas) continua a mesma, mas a API mudou em pontos que quebram código existente.

A forma mais simples de migrar é criar um projeto novo a partir do starter e trazer seus módulos, ajustando-os com a lista abaixo.

Mudanças que quebram código

1.x (Luvit) 2.0 (OpenResty)
ctx.json(200, dados), ctx.text, ctx.redirect... ctx:json(200, dados), ctx:text, ctx:redirect... (dois-pontos em todo o contexto)
app:listen(8080) e luvit app.lua app.lua retorna o app; o Nginx o executa (bin/crescent server start); a porta fica no listen do nginx.conf
middleware interrompe com return false middleware responde sem chamar next(): return ctx:error(401, ...)
middleware só global também por rota: auth.protect(middleware, action)
jwt.sign(..., { expiresIn = 900, notBefore = 0 }) opções em snake_case: expires_in, not_before
require("crescent.utils.jwt") require("crescent.security.jwt")
require("crescent.utils.hash"), hash.encrypt require("crescent.security.password"), password.hash / password.verify
require("crescent.utils.http") require("crescent.http_client")
require("crescent.utils.mail") require("crescent.mail")
require("crescent.utils.env") require("crescent.env") (e env NOME; no nginx.conf)
require("crescent.database.model") require("crescent.model")
Model:where(...):get() devolvia linhas devolve instâncias do model (use to_table() para JSON)
middleware static arquivos em public/, servidos pelo Nginx em /public/
middleware logger Crescent.middleware.request_log
luvit crescent-cli.lua <comando> lua cli.lua <comando> (ou bin/crescent <comando>)

O que continua valendo

  • Hashes de senha do 1.x (iteracoes$salt$hash) são verificados normalmente por password.verify. Use password.needs_rehash no login para atualizá-los para 600.000 iterações aos poucos.
  • Nomes camelCase do ORM (findOrFail, orderBy, whereIn, toTable...) continuam disponíveis como apelidos, mas a documentação usa snake_case.
  • crescent.utils.tests e o formato tests/test-*.lua continuam; rode com bin/crescent test.
  • O banco é o mesmo MySQL: suas tabelas continuam servindo. Confira as migrations antigas contra o formato novo (up/down retornando SQL; veja Migrations).

Pontos de atenção

  • Estado global: o app.lua roda uma vez por worker e vários workers atendem em paralelo. Estado em variáveis de módulo não é compartilhado entre workers; use o banco ou ngx.shared.
  • Variáveis de ambiente: declare cada uma com env NOME; no nginx.conf, senão os workers não as enxergam.
  • I/O: use as bibliotecas do OpenResty (cosockets): crescent.http_client, crescent.mail, lua-resty-*. Módulos do Luvit (coro-http, fs assíncrono...) não funcionam.
  • Erros: os erros gerados pelo framework (404, 405, validação, autenticação...) seguem o formato { status, code, error, details }; ajuste clientes que dependiam das respostas antigas.
