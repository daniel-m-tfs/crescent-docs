BBenchmark

Medido, não prometido.

Quatro aplicações com exatamente os mesmos endpoints — o Crescent 2.0, o Crescent 1.x, Node.js com Fastify e Python com FastAPI — medidas uma de cada vez, na mesma máquina, contra o mesmo MySQL e com a mesma carga.

    02Metodologia

    Regras iguais para todos.

    Comparação justa vale mais que número bonito. Estas são as regras — e, logo abaixo, os limites do que estes números dizem.

    Tudo é reproduzível: o repositório do benchmark tem as quatro aplicações, o script que mede e os resultados desta rodada.

    Uma por vez
    Só uma aplicação ligada durante a medição. O banco é recriado com as mesmas 1000 linhas antes de cada uma.
    Mesma carga
    wrk -t2 -c64, aquecimento descartado e janela medida igual para todos os cenários.
    Repetições
    Os números publicados vêm de uma rodada única. Entre execuções, o mesmo app variou até ~25% nesta máquina, então diferenças pequenas são empate. O script já faz repetições (--rounds 3, com a ordem das aplicações alternada e a mediana); esta página será atualizada com essa rodada.
    Só o núcleo
    Sem log de acesso, CORS, rate limit ou headers de segurança em nenhuma das quatro.
    Produção
    Crescent 2 com cache de código e app montada no boot; Node com NODE_ENV=production; uvicorn com uvloop e httptools.
    Workers
    “1 worker” é a comparação direta. Em “4 workers”: worker_processes 4, node:cluster com 4 processos e uvicorn --workers 4. O 1.x (Luvit) roda num processo só e fica de fora.
    Banco
    64 conexões no total para todos. SQL parametrizado direto no driver de cada stack; o cenário “ORM” mostra o custo extra do Model do Crescent.
    Contrato
    Antes de medir, cada aplicação passa por uma checagem: as respostas precisam ser iguais. Se falhar, ela não é medida.

    Limites — leia antes de citar

    • Carga, banco e aplicação rodam na mesma máquina e disputam CPU — com 4 workers isso pesa mais. Os números comparam as aplicações entre si; não são capacidade de produção.
    • O MySQL é local e as consultas são triviais. Numa aplicação real o banco costuma ser o gargalo, e as diferenças entre frameworks encolhem.
    • O mysql2 (Node) usa prepared statements do servidor; os outros usam o protocolo de texto com valores escapados — o jeito idiomático de cada driver.
    • O Crescent 1.x usa luasql, um driver bloqueante: durante uma consulta o processo inteiro espera.
    • Sem TLS e sem proxy na frente.
